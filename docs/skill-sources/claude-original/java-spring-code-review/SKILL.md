## Spring AOP is proxy-based - self-invocation silently disables it

Source: [Spring Framework reference - Proxying Mechanisms](https://docs.spring.io/spring-framework/reference/core/aop/proxying.html) (official).

Every annotation-driven cross-cutting concern in Spring (`@Transactional`, `@Cacheable`, `@CircuitBreaker`, `@Retry`, `@Async`, `@Secured`, ...) works by wrapping the **bean** in a proxy at context-startup. The proxy only intercepts calls that arrive **from outside the bean**. If method A on a bean calls method B on the *same* bean (`this.b()` or a bare `b()` call, even if B is public), that call goes directly to the target object, never through the proxy - so B's annotation is **silently a no-op**, not an error, not a warning. Official recommended fixes, in order of preference: refactor so the self-invocation doesn't happen (e.g. move B to a different bean the caller injects), inject a self-reference and call through that, or (last resort, discouraged) `AopContext.currentProxy()`.

**What this means for a review**: before "moving" a resilience/transaction/cache annotation from one method to another, check whether the new home is called *by another bean* or *by itself*. Moving `@CircuitBreaker` from a Feign client interface method onto a private helper inside the very service class that calls it looks like a clean refactor and is actually a regression - the breaker stops working with no test failure to catch it (unless a test specifically simulates the failure and checks the breaker actually opens, like this project's `MellatBaseDataResilienceIT` does - lean on tests like that rather than reading the annotation and assuming it fires).

## Resilience4j + Feign: three placements exist, they are NOT interchangeable

Sources: [resilience4j's own Feign integration docs](https://resilience4j.readme.io/docs/feign) (`Resilience4jFeign.builder()` + `FeignDecorators`, built at client-construction time, no annotations at all), [Spring Cloud OpenFeign reference](https://docs.spring.io/spring-cloud-openfeign/docs/current/reference/html/) (`spring.cloud.openfeign.circuitbreaker.enabled=true` wraps every Feign method automatically, naming each breaker `<FeignClientClass>#<method>(<paramTypes>)`), and the community-observed pattern of annotating a `@Service` method that calls a plain Feign client (what most tutorials/the [resilience4j-spring-boot-demo](https://github.com/resilience4j/resilience4j-spring-boot-demo) show, and what a [historical resilience4j GitHub issue](https://github.com/resilience4j/resilience4j/issues/559) flags as a rough edge specifically for annotating `@FeignClient` interfaces directly).

None of these three is universally "correct" - they trade off differently:

1. **Spring Cloud's own `circuitbreaker.enabled=true`** - zero annotations, but the auto-generated breaker *name* is tied to the Feign method signature, which won't match a hand-written `resilience4j.circuitbreaker.instances.<name>` config block unless you let Spring Cloud dictate the name. If you need a *specific*, stable, human-chosen instance name (to match existing `application.yml` config, dashboards, alerts), this doesn't give you one without extra `alphanumeric-ids` config gymnastics.
2. **resilience4j's own Feign builder** - full control, no AOP/proxy involved at all (decorators wrap the Feign client at construction), but it's a different construction path than a Spring-managed `@FeignClient` bean and doesn't compose with Spring DI as naturally.
3. **`resilience4j-spring`'s generic `@CircuitBreaker`/`@Retry` AOP annotations, placed on a `@FeignClient` interface method** - works because the Feign client is *itself* a genuine, separate Spring bean (registered by `FeignClientFactoryBean`), so calling it from a service is a normal cross-bean call, not self-invocation. Gives you a stable, named instance matching hand-written config. This is what this project uses (see `MellatBaseDataClient`/`MellatAccountClient`'s own class Javadoc for the specific reasoning already written down).

**Before "moving these to the service layer"**, trace what happens to the *exception the annotation's retry/circuit-breaker predicate actually sees*. In this project specifically: `MellatTransientFailurePredicate` (referenced by class name from `application.yml`, shared across the `mellatAuth`/`mellatBaseData`/`mellatAccount` instances) pattern-matches on the **raw** `MellatApiException`/`feign.RetryableException`/`IOException` - the types a Feign call throws *before* `MellatErrorMapper` translates them into this service's own `MellatServiceException`. If `@CircuitBreaker`/`@Retry` moved to wrap a point *after* that translation (e.g. a `MellatBaseDataService`/`MellatAccountService` method that internally calls `errorMapper.call(...)`), the predicate would only ever see the *already-translated* `MellatServiceException` - it would need rewriting to match on `MellatErrorCode` instead, which additionally means `MellatTransientFailurePredicate` (living in the `client` package) would need to import a `service.error` type - a `client` → `service` dependency that `TechnicalStructureTest`'s own ArchUnit rule (`client` may only be *accessed by* `service`, never the reverse) explicitly forbids and enforces on every build. So in this codebase, moving these annotations off the Feign interface isn't just a style question - it either silently breaks retry/circuit-breaking (self-invocation, if placed on a private same-class helper) or fails the build (ArchUnit layering, if placed correctly and the predicate is updated to match). Keeping them on the Feign client interface, as documented in its own Javadoc, is the placement that is actually consistent with this project's specific architecture - don't move it without solving both problems at once, and say so explicitly if you decide to leave it as-is after checking.

## Layered architecture (controller → service → repository/client)

Sources: general Spring Boot community consensus (Baeldung, Spring guides, multiple independent write-ups converge on the same shape) - controllers parse/validate the HTTP boundary and delegate, never contain business logic; the service layer owns business rules and orchestrates calls to repositories/external clients; the repository/client layer only knows how to reach the data source/external system, nothing about why. This project's own `TechnicalStructureTest` encodes exactly this as enforced ArchUnit rules (`config`/`client`/`web`/`service`/`security` - see `CLAUDE.md`'s "Enforced layering" section) - treat that test suite as the authoritative, checkable version of "layering is correct" for this repo, not a general impression.

## Checklist for a "clean up the code" pass

- Run `./mvnw verify` once before touching anything, to get a clean baseline (a pre-existing failure isn't yours to fix silently).
- For every annotation-driven cross-cutting concern (`@Transactional`, `@Cacheable`, `@CircuitBreaker`, `@Retry`, `@Async`), confirm the annotated method is reachable only via a cross-bean call, never self-invoked.
- For every proposed move of such an annotation, trace what exception/return type actually crosses the AOP boundary at the *new* location, and whether anything downstream (a predicate, a matcher, ArchUnit) assumed the *old* location's type.
- Prefer citing this project's own enforced tests (`TechnicalStructureTest`, the resilience ITs) over a general impression of "how Spring apps are usually structured" - a convention that's common elsewhere can still be wrong for this specific, already-tested design.
- When a finding turns out to be genuinely stylistic (both placements work correctly, no test/layering conflict), say so and let the user decide rather than "fixing" it silently.
